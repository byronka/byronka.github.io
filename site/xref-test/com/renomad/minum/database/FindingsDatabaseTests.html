85      /**
86       * FINDING 1: {@link Db#stop()} silently discards queued writes, losing data.
87       * <br>
88       * Defect: Db.java:384 and Db.java:393 - {@link Db#stop()} delegates to
89       * {@link com.renomad.minum.queue.ActionQueue#stop(int, long)} with a count of 5 and a sleep
90       * of 20 milliseconds.  ActionQueue.java:125-131 loops at most 5 times, waiting 20
91       * milliseconds each time, and then simply returns while the queue still holds a backlog.
92       * The framework's own shutdown ({@link com.renomad.minum.queue.ActionQueueKiller#killAllQueues()})
93       * then interrupts the writer thread, and every remaining queued write is discarded with
94       * no error and no log of the lost data.
95       * <br>
96       * Correct behavior: {@link Db#stop()} is documented as waiting "for our threads to finish
97       * their work".  When it returns, every record that was accepted by {@link Db#write(DbData)}
98       * must be durable on disk.  Shutting a database down must never silently lose accepted writes.
99       * <p>
100      * BK: The analysis is correct about its result, but misunderstands the bigger picture.
101      * There are two databases in Minum, "Db" and "DbEngine2".
102      * "Db" is no longer recommended to be used, as it does not provide the
103      * performance or correctness guarantees of "DbEngine2".
104      * </p>
105      * <p>
106      * It is kept around for legacy programs.  "Db" was designed as a demonstration
107      * of the simplest-possible approach for storing data, and under ordinary
108      * conditions it will succeed.
109      * </p>
110      * <p>
111      * Tests like this stress it far beyond its design parameters, writing 20,000 records
112      * and then immediately shutting down.
113      * </p>
114      * <p>
115      * The new database engine, "DbEngine2", would handle this perfectly.
116      * </p>
117      */

381     /**
382      * FINDING 6: when a load fails part way through, the automatic retry double-adds rows to the
383      * registered indexes.
384      * <br>
385      * Defect: {@link Db#loadData()} (Db.java:300-315) leaves the rows that were read before the
386      * failure in the in-memory map and in the registered index buckets, while leaving
387      * {@code hasLoadedData} false.  Every read method ({@link Db#values()},
388      * {@link Db#getIndexedData(String, String)}, ...) automatically retries the load, and
389      * {@link Db#readAndDeserialize(java.nio.file.Path)} (Db.java:281) calls
390      * {@link AbstractDb#addToIndexes(DbData)} again for the rows that were already indexed.  The
391      * index bucket now holds two objects for one row, so
392      * {@link AbstractDb#findExactlyOne(String, String)} throws "More than one item found" for
393      * data that exists exactly once.
394      * <br>
395      * Correct behavior: a failed load must not leave partial state behind (or the retry must
396      * clear it first), so that once the transient I/O problem clears, the loaded database is
397      * exactly as if the load had succeeded the first time: one index entry per row.
398      * <p>
399      *     BK: updated the loadData methods in Db and DbEngine2 so that their internal
400      *     data collections are clean and ready before loading the data, so that in
401      *     the negative case of a failure during load, the next time around will have
402      *     clean data before starting.
403      * </p>
404      */

445     /**
446      * FINDING 7: the shared {@link java.text.SimpleDateFormat} is not thread-safe.
447      * <br>
448      * Defect: DatabaseAppender.java:33 declares
449      * {@code static final SimpleDateFormat simpleDateFormat}.  SimpleDateFormat is documented as
450      * not thread-safe (it keeps mutable parsing/formatting state in a shared Calendar), yet this
451      * single instance is shared by every {@link DatabaseAppender} and every
452      * {@link DatabaseConsolidator} in the JVM.  Each database has its own appender and
453      * consolidator, and each consolidation runs on its own thread, so real deployments format
454      * (DatabaseAppender.java:207, DatabaseConsolidator.java:73 and :84) and parse
455      * (DatabaseConsolidator.java:322) concurrently.  The result is malformed append-log file
456      * names, mis-parsed file names (so append logs are consolidated out of order, which loses the
457      * "last write wins" ordering guarantee), and spurious exceptions.
458      * <br>
459      * Correct behavior: date formatting must be thread-safe - for example a
460      * {@link java.time.format.DateTimeFormatter}, or a per-instance / ThreadLocal
461      * SimpleDateFormat.  Concurrent formatting and parsing must always produce correct results.
462      * // BK: fixed by switching to use shared static DateTimeFormatter declared in AbstractDb
463      */
464     @Test
465     public void test_Finding_SharedSimpleDateFormatIsThreadSafe() throws Exception {
466         String knownFileName = "2025_08_30_13_01_49_123";
467         Instant knownDate = DATE_TIME_FORMATTER.parse(knownFileName, Instant::from);
468 
469         int threadCount = 8;
470         int iterations = 20_000;
471         List<String> anomalies = Collections.synchronizedList(new ArrayList<>());
472         var startingLine = new CountDownLatch(1);
473         var futures = new ArrayList<Future<?>>();
474 
475         try (ExecutorService executor = Executors.newFixedThreadPool(threadCount)) {
476             for (int i = 0; i < threadCount; i++) {
477                 // half the threads format dates (as the appender and consolidator do),
478                 // half parse file names (as the consolidator does)
479                 boolean isFormatter = i % 2 == 0;
480                 futures.add(executor.submit(() -> {
481                     startingLine.await();
482                     for (int j = 0; j < iterations && anomalies.isEmpty(); j++) {
483                         if (isFormatter) {
484                             try {
485                                 String formatted = DATE_TIME_FORMATTER.format(knownDate);
486                                 if (!knownFileName.equals(formatted)) {
487                                     anomalies.add("formatting produced \"" + formatted + "\" instead of \"" + knownFileName + "\"");
488                                 }
489                             } catch (Exception ex) {
490                                 anomalies.add("formatting threw " + ex);
491                             }
492                         } else {
493                             try {
494                                 List<Instant> instants = DatabaseConsolidator.convertFileListToInstantList(new String[]{knownFileName});
495                                 if (!knownDate.equals(instants.getFirst())) {
496                                     anomalies.add("parsing \"" + knownFileName + "\" produced " + instants.getFirst() +
497                                             " instead of " + knownDate);
498                                 }
499                             } catch (Exception ex) {
500                                 anomalies.add("parsing threw " + ex);
501                             }
502                         }
503                     }
504                     return null;
505                 }));
506             }
507             startingLine.countDown();
508             for (Future<?> future : futures) {
509                 future.get();
510             }
511         }
512 
513         assertTrue(anomalies.isEmpty(),
514                 "Formatting and parsing database append-log file names concurrently must always produce " +
515                         "correct results.  Anomalies seen: " + anomalies);
516     }

522     /**
523      * counts the data files (e.g. "1.ddps") in a classic database directory,
524      * excluding the index file.
525      */
526     private static long countDatabaseFiles(Path databaseDirectory) throws IOException {
527         try (Stream<Path> files = Files.list(databaseDirectory)) {
528             return files
529                     .map(x -> x.getFileName().toString())
530                     .filter(x -> x.endsWith(Db.DATABASE_FILE_SUFFIX))
531                     .filter(x -> !x.equals("index" + Db.DATABASE_FILE_SUFFIX))
532                     .count();
533         }

546     /**
547      * Retrieves the current number of open OS handles for this Java process.
548      */
549     public static long getOpenHandleCount() {
550         // 1. Get the current Java process ID
551         long pid = ProcessHandle.current().pid();
552 
553         try {
554             // 2. Query Windows tasklist to get the handle count for this specific PID
555             Process process = new ProcessBuilder(
556                     "cmd.exe", "/c",
557                     "tasklist /FI \"PID eq " + pid + "\" /V /FO LIST"
558             ).start();
559 
560             try (BufferedReader reader = new BufferedReader(new InputStreamReader(process.getInputStream()))) {
561                 String line;
562                 while ((line = reader.readLine()) != null) {
563                     // Look for the "Handles:" line in the output (localized to Windows OS language)
564                     if (line.contains("Handles:") || line.toLowerCase().contains("handle")) {
565                         String countStr = line.replaceAll("[^0-9]", "").trim();
566                         if (!countStr.isEmpty()) {
567                             return Long.parseLong(countStr);
568                         }
569                     }
570                 }
571             }
572 
573             // Alternative fallback using powershell if tasklist doesn't expose it on your Windows version
574             return getHandleCountViaPowerShell(pid);
575 
576         } catch (Exception e) {
577             throw new RuntimeException("Failed to read Windows handle count", e);
578         }
579     }
580 
581     private static long getHandleCountViaPowerShell(long pid) {
582         try {
583             Process process = new ProcessBuilder(
584                     "powershell.exe", "-Command",
585                     "(Get-Process -Id " + pid + ").HandleCount"
586             ).start();
587 
588             try (BufferedReader reader = new BufferedReader(new InputStreamReader(process.getInputStream()))) {
589                 String line = reader.readLine();
590                 if (line != null) {
591                     return Long.parseLong(line.trim());
592                 }
593             }
594         } catch (Exception ignored) {}
595         return -1;
596     }
